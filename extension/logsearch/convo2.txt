  ---
  What an inverted index is and when it helps

  Inverted index = map from values → row IDs. For each distinct value (or token)
   in a column, store sorted list of rows containing it.

  Core data structures:
  1. Term dictionary — sorted mapping: term → posting list location
  2. Posting lists — compressed sorted row ID sets per term (roaring bitmaps
  ideal)
  3. Optional: positions within rows (for phrase queries), term frequencies (for
   BM25)

  When would it be used?

  Your intuition about WHERE varchar_column = 'some_string' is partially right —
   but that's not where an inverted index shines most. Let me break down the
  query patterns:

  Query Pattern: WHERE col = 'exact_value'
  Best Index: ART (already exists)
  Why: Point lookup on exact value. ART is designed for this. Inverted index
    works too but adds complexity for no gain.
  ────────────────────────────────────────
  Query Pattern: WHERE col LIKE '%error%'
  Best Index: Inverted index (tokenized)
  Why: Full scan today. If "error" is a token, inverted index finds it directly.

    Substring needs n-grams.
  ────────────────────────────────────────
  Query Pattern: WHERE contains_token(msg, 'error')
  Best Index: Inverted index
  Why: Primary use case. Look up "error" in dictionary → read posting list →
    done.
  ────────────────────────────────────────
  Query Pattern: WHERE contains_all_tokens(msg, 'error', 'timeout')
  Best Index: Inverted index
  Why: Intersect posting lists for each token. Roaring bitmap AND.
  ────────────────────────────────────────
  Query Pattern: WHERE trace_id = 'abc-123' on 100M distinct values
  Best Index: Either
  Why: ART works but gets large. Inverted index with one-entry posting lists
    works too. For log use cases with ultra-high-cardinality IDs, bloom filters
    may beat both.
  ────────────────────────────────────────
  Query Pattern: WHERE service = 'api' AND level = 'ERROR' AND msg CONTAINS 
    'timeout'
  Best Index: Compound
  Why: Timestamp prune → zone map check on service/level → inverted index on
  msg.
    Composition matters most.

  Key insight: for log search, the inverted index is most valuable for text 
  columns where ART doesn't help (you wouldn't build an ART on a message
  column). ART handles structured fields fine. The inverted index's power is
  tokenized search — breaking text into tokens and enabling fast
  lookup/intersection.

  Build new vs. reuse DuckDB primitives

  This is the critical design question. Let me map inverted index operations to
  DuckDB's architecture:

  What DuckDB already gives you (reuse):

  1. Columnar storage with row groups (~122K rows) — natural segmentation unit
  for per-segment indexes
  2. Zone maps (min/max per row group) — timestamp pruning before index is
  consulted
  3. Vectorized execution — consuming a row ID bitset as a selection vector is
  native
  4. BoundIndex interface + IndexType registration — lifecycle management
  (create, persist, drop, transaction awareness)
  5. Parallel build infrastructure — build_sink/build_combine/build_finalize
  callbacks map cleanly to inverted index construction (each thread tokenizes +
  builds local posting lists → merge)
  6. FixedSizeAllocator — memory management for index nodes

  What you must build new:

  1. Term dictionary — sorted, block-compressed, with sparse lookup. ART's radix
   tree structure doesn't map well to inverted index term lookup. A sorted
  dictionary with front-coding + sparse index (like ClickHouse) is purpose-built
   for this.
  2. Posting lists with roaring bitmaps — ART stores single row IDs per key. You
   need sets of row IDs per term, with efficient AND/OR/NOT. Roaring bitmaps are
   the standard choice (CRoaring library is C, battle-tested).
  3. Tokenizer — DuckDB has no general tokenizer. Need: split-on-non-alpha,
  configurable separators, case folding, log-aware tokenization (IPs, UUIDs,
  dotted paths).
  4. Query-time posting list intersection logic — the boolean query engine that
  takes term1 AND term2 OR term3 and composes roaring bitmap operations.
  5. Index-to-scan bridge — translating posting list results into something
  DuckDB's execution engine can consume efficiently (selection vectors or row ID
   vectors).

  What's borderline (could go either way):

  1. Persistence — You could use DuckDB's IndexStorageInfo + FixedSizeAllocator
  (like ART does) or manage your own files. ART's allocator model works for tree
   nodes; dictionary blocks + posting list blocks have different access
  patterns. I'd lean toward custom serialization with DuckDB's block manager for
   the actual I/O.
  2. The BoundIndex interface itself — It provides lifecycle + transaction
  integration for free, but its query interface (TryInitializeScan → Scan
  returning row IDs) is designed for simple point/range lookups. For multi-token
   boolean queries, you'd need to either (a) stretch this interface or (b)
  provide a parallel query path.

  Integration architecture — my recommendation

  Two-layer design:

  Layer 1: Native BoundIndex (lifecycle + simple queries)

  Implement BoundIndex subclass. Register via IndexType. This gives you:
  - CREATE INDEX idx ON table USING inverted(column) — DDL syntax for free
  - Automatic Append/Insert on data changes (incremental update)
  - Persistence via SerializeToDisk/SerializeToWAL
  - Transaction-aware drop/vacuum

  Build callbacks:
  build_sink:     tokenize chunk → insert into thread-local hash map (term →
  row_id list)
  build_combine:  merge local hash maps into global
  build_finalize: sort dictionary, compress posting lists to roaring bitmaps,
  produce BoundIndex

  For simple queries (WHERE contains_token(col, 'error')), implement
  TryInitializeScan that:
  1. Looks up term in dictionary
  2. Reads posting list
  3. Returns row IDs

  This plugs into the existing table scan path — but requires extending
  table_scan.cpp beyond ART-only. Current code at line ~717 checks specifically
  for ART. Needs generalization.

  Layer 2: Custom functions for complex queries

  For multi-token queries, boolean composition, or "direct read" optimization,
  provide explicit functions:

  -- Returns row IDs matching the query
  SELECT * FROM table WHERE rowid IN (
      inverted_search('table', 'column', 'error AND timeout')
  );

  -- Or better, as a table function that produces filtered results directly:
  SELECT * FROM inverted_scan('table', 'error AND timeout NOT debug',
      columns := ['timestamp', 'service', 'message']);

  This bypasses the optimizer's limited index-scan path and gives full control
  over:
  - Multi-token boolean evaluation
  - Direct-read optimization (skip decoding message column if query doesn't need
   it)
  - Streaming partial results

  Over time, push more of this into the optimizer via pushdown_complex_filter
  hooks.

  What to build first

  For a first step, I'd suggest:

  MVP: Per-row-group inverted index with single-token lookup

  1. Tokenizer — simple split-on-non-alphanumeric + case fold. Minimal but
  functional.
  2. Dictionary — sorted vector<string> with binary search (optimize to
  block-compressed later).
  3. Posting lists — roaring bitmaps via CRoaring.
  4. Build path — given a column of VARCHAR, tokenize every row, produce
  dictionary + posting lists.
  5. Query path — contains_token(col, 'term') → look up term → return roaring
  bitmap → convert to selection vector.
  6. Persistence — serialize dictionary + posting lists to DuckDB blocks.

  Skip for now: multi-token boolean queries, n-grams, phrase queries, BM25,
  incremental update. Add these once the core data structures work.

  Timestamp Pruning Design

  Key insight: logs arrive roughly in timestamp order, so row IDs correlate with
   timestamps. DuckDB stores data in row groups (~122K rows each). If row group
  0 has timestamps [00:00, 00:05] and row group 1 has [00:05, 00:10], a query
  for ts > 00:07 can skip row group 0 entirely.

  Structure the inverted index per row group:

  Index on "message", timestamp_column = "ts"
  │
  ├── segment[0]  (row_start: 0,      ts: [Jan 1 00:00, Jan 1 00:05])
  │   ├── dictionary: {"error"→0, "timeout"→1, "warning"→2}
  │   └── postings:   [0]→{3,45,1200}  [1]→{7,89}  [2]→{500}
  │
  ├── segment[1]  (row_start: 122880, ts: [Jan 1 00:05, Jan 1 00:10])
  │   ├── dictionary: {"error"→0, "connection"→1}
  │   └── postings:   [0]→{12,300,501}  [1]→{44}
  │
  └── segment[2]  (row_start: 245760, ts: [Jan 1 00:10, Jan 1 00:15])
      └── ...

  Query WHERE contains(message, 'error') AND ts > '00:07':
  1. Iterate segments, check [ts_min, ts_max] vs query range
  2. Segment 0: ts_max=00:05 < 00:07 → skip
  3. Segment 1: overlaps → look up "error" → postings {12,300,501} → global IDs
  {122892, 123180, 123381}
  4. Segment 2: contained → look up "error" → return its postings
  5. Return union. DuckDB's WHERE ts > '00:07' does fine-grained filtering on
  surviving rows.

  Two-level pruning: inverted index skips whole segments (cheap min/max
  compare), DuckDB handles exact timestamp filtering on remaining rows.

  Per-segment dictionaries (not one global dictionary) — segments are
  independent, can be serialized to disk independently later, align with
  DuckDB's row group model.

  Segment approach — detailed

  What "segments" mean here

  Not DuckDB storage segments. My "segments" are internal partitions of the 
  inverted index, aligned with DuckDB row groups. One BoundIndex object covers
  the whole table. Inside it, the data is partitioned:

  BoundIndex (one per table)
   └── InvertedIndex
        ├── partition[0]  ← aligned with row group 0 (rows 0–122879)
        │   ├── ts_min, ts_max
        │   ├── dictionary: {"error"→0, "timeout"→1}
        │   └── postings: [0]→{3,45,1200}, [1]→{7,89}
        │
        ├── partition[1]  ← aligned with row group 1 (rows 122880–245759)
        │   ├── ts_min, ts_max
        │   ├── dictionary: {"error"→0, "null_ptr"→1}
        │   └── postings: [0]→{12,300}, [1]→{44}
        │
        └── partition[2]  ← aligned with row group 2
            └── ...

  Each partition has its own dictionary and own posting lists. Posting lists
  store local offsets (0 to ~122K), converted to global row IDs at query time:
  global_id = partition.row_start + local_offset.

  Why per-row-group?

  1. Timestamp pruning becomes segment skip. Skip entire partition if [ts_min, 
  ts_max] doesn't overlap query range. Cheapest possible prune — two
  comparisons.
  2. Future persistence. Each partition serializes independently. Load only
  partitions you need from disk. This is the same pattern as Husky fragments,
  ClickHouse parts, Quickwit splits.
  3. Incremental build. New row group → new partition. No global rebuild.
  4. Bounded memory per partition. Dictionary + posting lists for ~122K rows is
  small. Fits in cache nicely.

  How row group alignment works during build

  During build_sink, we receive DataChunks with row IDs. Row IDs encode row
  group membership:

  // DuckDB row ID layout
  idx_t row_group_idx = row_id / ROW_GROUP_SIZE;  // which row group
  idx_t local_offset = row_id % ROW_GROUP_SIZE;   // offset within row group

  So during build, for each row:
  1. Compute row_group_idx from row ID
  2. Tokenize text value
  3. For each token, add local_offset to that token's posting list in
  partitions[row_group_idx]

  Getting timestamp min/max

  During build_finalize, we have access to DataTableInfo → table storage → row
  group metadata → column statistics (zone maps). Read timestamp column min/max
  per row group, store in each partition.

  Alternatively: scan timestamp column during build. Add timestamp as a second
  expression in the index (CREATE INDEX ... USING fts(message, ts)) but treat it
   as metadata, not tokenized. The build callbacks receive both columns.

  I lean toward reading zone maps in finalize — cleaner separation, no need to
  receive timestamp data during sink.

  What happens when row groups are rewritten?

  Three scenarios:

  Event: New rows inserted
  What happens: BoundIndex::Append() called with new DataChunk + row IDs
  Index impact: Tokenize, add to existing or new partition
  ────────────────────────────────────────
  Event: Rows deleted
  What happens: BoundIndex::TryDelete() called with row IDs
  Index impact: Mark deleted in a bitset per partition. Exclude during search.
  ────────────────────────────────────────
  Event: Compaction/checkpoint
  What happens: Row groups may be reorganized, row IDs may change
  Index impact: Index must be rebuilt for affected partitions. For in-memory
  MVP:
     full rebuild is acceptable. Later: integrate with checkpoint hooks.

  For the MVP, Append handles new data. Deletes via bitset. Compaction triggers
  rebuild. This matches how the current FTS extension works (rebuild on change).

  Selectivity / term frequency fallback (question #2)

  Two-level decision:

  At index build time: Store document frequency per term per partition.
  struct PartitionEntry {
      unordered_map<string, uint32_t> term_doc_freq;  // "error" → 342 docs in 
  this partition
      idx_t total_rows;  // 122880
  };

  At query time (optimizer rule):
  1. Query has contains(msg, 'error') on indexed column
  2. Look up "error" in index → compute global selectivity: sum(df) / 
  sum(total_rows)
  3. If selectivity > threshold (say 5%): don't rewrite. Leave original
  contains() filter. DuckDB does full scan.
  4. If selectivity < threshold: rewrite to rowid IN (inverted_search(...)).
  Index returns row IDs, DuckDB fetches only those rows.

  For compound queries like contains(msg, 'error') AND contains(msg, 'the'):
  - "error" has 0.1% selectivity → use index
  - "the" has 90% selectivity → skip
  - Rewrite only the selective term. Keep "the" as post-filter on surviving
  rows.

  No subset of posting list needed. It's all-or-nothing per term: either use the
   index (return full posting list) or don't (fall through to scan). The
  threshold prevents the bad case of returning millions of row IDs.

  Later optimization: even for common terms, the index can help if the
  intersection is selective. contains(msg, 'the') AND contains(msg, 'error') —
  "the" alone is huge, but "the" ∩ "error" is small. That's a phase-2
  optimization.

  Posting list intersection

  DuckDB's merge join operates on DataChunks/Vectors — too heavy for raw integer
   merges. Custom merge is better. ~15 lines:

  // Both inputs sorted. Output sorted.
  void Intersect(const vector<uint32_t> &a, const vector<uint32_t> &b, 
  vector<uint32_t> &out) {
      idx_t i = 0, j = 0;
      while (i < a.size() && j < b.size()) {
          if (a[i] == b[j]) { out.push_back(a[i]); i++; j++; }
          else if (a[i] < b[j]) { i++; }
          else { j++; }
      }
  }

  For multi-segment queries (same term across row groups): concatenate, not
  intersect. Row IDs from partition N are all smaller than partition N+1, so
  concatenation preserves sorted order. Intersect is for different terms (AND).

  NOT expressions

  For NOT contains(msg, 'error'):
  - Need complement of posting list = all rows NOT in it
  - With sorted vectors, requires materializing complement: iterate [0,
  row_count), skip entries in posting list. O(row_count) — expensive.
  - This is where roaring bitmaps shine (bitwise NOT is near-free).

  MVP: don't handle NOT in the index. If query has NOT, don't rewrite that
  predicate. Positive terms get index-accelerated, NOT stays as post-filter.
  Note for later.

  Positional index / phrase queries

  Correct — not needed. For 'connection timeout':
  1. Index finds rows with "connection" AND "timeout" (intersect posting lists)
  2. Original contains(msg, 'connection timeout') filter remains as post-filter
  for exact phrase
  3. Index narrows candidates, scan verifies. Good enough.

  What is roaring?

  Problem: You have a posting list of row IDs. Options:

  ┌──────────────────┬───────────────────┬──────────────────┬──────────────┐
  │                  │  Space for 1000   │                  │              │
  │    Structure     │  IDs out of 10M   │    AND speed     │ NOT support  │
  │                  │     possible      │                  │              │
  ├──────────────────┼───────────────────┼──────────────────┼──────────────┤
  │ Sorted array     │ 4KB               │ O(n+m) merge     │ O(universe)  │
  │ uint32[]         │                   │                  │ — bad        │
  ├──────────────────┼───────────────────┼──────────────────┼──────────────┤
  │ Raw bitmap (1    │                   │ O(universe/64)   │ O(1) flip    │
  │ bit per possible │ 1.25MB            │ bitwise          │ bits         │
  │  ID)             │                   │                  │              │
  ├──────────────────┼───────────────────┼──────────────────┼──────────────┤
  │ Hash set         │ ~40KB (overhead)  │ O(min(n,m))      │ O(universe)  │
  │                  │                   │                  │ — bad        │
  └──────────────────┴───────────────────┴──────────────────┴──────────────┘

  Both extremes lose: arrays waste time on NOT/dense data, bitmaps waste space
  on sparse data.

  Roaring bitmap splits the 32-bit ID space into chunks of 65536 (upper 16 bits
  = chunk key, lower 16 bits = position within chunk). Each chunk independently
  chooses its representation:

  Chunk 0 (IDs 0–65535):     sparse, 12 values  → sorted uint16 array [12
  entries, 24 bytes]
  Chunk 1 (IDs 65536–131071): dense, 40000 values → bitset [8KB]
  Chunk 2 (IDs 131072–196607): full, all 65536    → run-length [just the count]
  Chunk 3: empty                                   → not stored at all

  Operations work chunk-by-chunk, picking the optimal algorithm:
  - AND of two sparse chunks: sorted merge
  - AND of two dense chunks: bitwise AND on 8KB bitsets (SIMD-friendly: 128 AND
  instructions)
  - AND of sparse + dense: binary lookup into bitset
  - NOT: flip the bitset, or compute complement of small array

  This gives near-optimal performance for any density. CRoaring library
  implements this. Used by ClickHouse, Lucene, Spark, Druid.

  For MVP: sorted vector<uint32_t> behind a PostingList abstraction. Swap to
  roaring when we need NOT or performance matters on dense lists. The interface
  stays the same.

  Buffer pool tracking

  Use DuckDB's allocator for large allocations (posting list backing arrays).
  For MVP: track memory usage in GetInMemorySize(), use Allocator::Get(db) where
   practical. Full buffer-pool-managed blocks (like ART's FixedSizeAllocator) is
   a later optimization.

⏺ Late Materialization & Selection Vectors — Relevance

  Selection vectors: Array of indices mapping logical positions → physical row
  positions. Instead of physically removing non-matching rows from a DataChunk,
  DuckDB just updates the selection vector. All downstream operators see only
  "active" rows. Zero-copy filtering.

  DataChunk with 8 rows, SelectionVector = [0, 2, 5]
  → downstream sees only rows 0, 2, 5. No data copied.

  Late materialization: Split a table scan into two phases:
  1. Phase 1: Read only filter columns + rowid. Apply filters. Get surviving row
   IDs.
  2. Phase 2: Fetch remaining columns only for surviving rows.

  If filter kills 99% of rows, you avoid reading 99% of non-filter column data.

  Very relevant to this project

  This is exactly the "direct read" optimization from ClickHouse. The inverted
  index produces a set of matching row IDs. With late materialization:

  1. Inverted index says: rows {122892, 123180, 123381} contain "error"
  2. DuckDB fetches only those rows' columns (timestamp, service, etc.)
  3. Text column (message) never decoded if not in SELECT

  Current index scan path already does this. DuckIndexScanState wraps row IDs in
   a Vector(LogicalType::ROW_TYPE) and calls DataTable::Fetch() — which reads
  only requested columns for those specific rows. This is late materialization
  by construction.

  Two integration paths for our extension:

  Approach: Mirror DuckIndexScanState
  How: Produce row_t[], call storage.Fetch()
  Pro: Natural, matches ART pattern, defers column reads
  Con: Tied to table_scan.cpp internals
  ────────────────────────────────────────
  Approach: rowid IN (subquery)
  How: Return row IDs from table function, let optimizer handle join
  Pro: Cleaner separation, works today
  Con: Optimizer may not pick most efficient join. Extra overhead of
    materializing row IDs as a result set

  For MVP, the rowid IN (...) approach works. Later, direct index scan
  integration (like ART) gives better performance because it skips the join
  overhead and naturally defers column reads.

  Key design implication: The inverted index should produce results as a sorted 
  array of row_t, not as a selection vector. Selection vectors are intra-chunk
  (max ~2048 entries). Row IDs span the whole table and feed into Fetch() which
  handles the row-group-level routing internally.

     Plan: logsearch Extension — Inverted Index for Log Message Search

     Context

     We're building a DuckDB extension specialized for full-text search on log
     messages. The existing FTS extension uses SQL tables (no native index
     integration, no incremental update, no time pruning). This extension uses
     DuckDB's native IndexType infrastructure to provide a proper inverted index
      with per-row-group partitioning and timestamp-based segment pruning.

     The goal for this first iteration: a working inverted index that can be
     created via CREATE INDEX, is used transparently via an optimizer rule, and
     prunes posting lists by timestamp range.

     Architecture

     CREATE INDEX idx ON logs USING logsearch(message) WITH (timestamp_column =
     'ts');

     -- User writes normal SQL, optimizer rewrites to use index:
     SELECT * FROM logs WHERE contains(message, 'error') AND ts > '2024-01-01'
     ORDER BY ts LIMIT 100;

     Internally:
     1. Build: Table scan → tokenize → build per-row-group posting lists
     2. Query: Optimizer detects filter on indexed column → queries inverted
     index → rewrites to rowid IN (matching_ids) via MARK join → DuckDB fetches
     only matching rows

     Data structures

     LogsearchIndex (BoundIndex subclass — one per table)
      └── partitions: vector<IndexPartition>
           ├── partition[0] — aligned with row group 0
           │   ├── row_start, row_count (from SegmentNode<RowGroup>)
           │   ├── ts_min, ts_max (from zone maps, optional)
           │   ├── dictionary: std::map<string, idx_t>  (term → posting_list_id)
           │   └── posting_lists: vector<PostingList>
           │        └── PostingList: sorted vector<uint32_t> (local offsets)
           ├── partition[1] — row group 1
           └── ...

     - Dictionary: std::map (ordered for serialization + prefix search via
     lower_bound)
     - Posting lists: sorted vector<uint32_t> of local offsets within the row
     group
       - D_ASSERT sorted invariant on every insert
       - Later: evaluate roaring bitmaps, skip lists, delta compression
     - Row group alignment: Use SegmentTree::TryGetSegmentIndex() to map row_id
     → partition, NOT row_id / ROW_GROUP_SIZE
     - Memory: Use Allocator::Get(db) for tracked allocations. GetInMemorySize()
      reports actual usage.

     Timestamp pruning

     Per partition, store ts_min/ts_max read from zone maps
     (RowGroup::GetStatistics(ts_column_idx) → NumericStats::GetMin/GetMax). At
     query time, skip partitions whose [ts_min, ts_max] doesn't overlap the
     query's timestamp range. DuckDB handles exact timestamp filtering on
     surviving rows.

     Tokenizer

     Simple for now:
     - Split on non-alphanumeric characters
     - Lowercase all tokens
     - Skip empty tokens and tokens of length 1
     - Note for later: log-aware tokenization (IPs, UUIDs, dotted paths, k=v
     pairs)
     - Note for later: reversed terms in dictionary for suffix search

     Posting list operations

     Custom merge operations (not DuckDB merge join — too heavyweight for raw
     integer arrays):
     - Intersect (AND): two-pointer merge, keep common elements
     - Union (OR): two-pointer merge, keep all elements
     - NOT: Not supported in index for MVP. Falls through to scan + filter.
     (Roaring bitmaps make this cheap later.)
     - Multi-segment: Same term across row groups → concatenate (already sorted
     since row IDs increase across partitions)

     Selectivity threshold

     Store document frequency per term per partition. At optimizer time:
     - selectivity = sum(df_for_term) / sum(total_rows) across partitions
     - If selectivity > 20%: don't rewrite, let DuckDB full-scan
     - For compound queries: rewrite only selective terms, keep non-selective as
      post-filter

     Step 5: Optimizer rule

     Registered as optimize_function (runs AFTER built-in optimizers).

     Algorithm:
     1. Walk logical plan recursively
     2. Find LogicalFilter over LogicalGet (table scan)
     3. For each filter expression, check if it references a column that has a
     logsearch index:
       - Access table via LogicalGet → catalog → DataTable → TableIndexList
       - Check each index: index.GetIndexType() == "logsearch" and column
     matches
     4. Pattern match filter expressions:
       - BoundComparisonExpression(=, col_ref, constant) → tokenize constant,
     intersect posting lists
       - BoundFunctionExpression("contains", col_ref, constant) → tokenize
     constant, intersect posting lists
       - BoundFunctionExpression("prefix", col_ref, constant) → prefix search in
      dictionary, union posting lists
       - col LIKE 'prefix%' → already rewritten by DuckDB to prefix comparison;
     catch prefix pattern
     5. Extract timestamp bounds from co-occurring filter expressions (if
     timestamp column configured):
       - Find ts >= val, ts > val, ts <= val, ts < val comparisons
       - Pass bounds to index search for segment pruning
     6. Check selectivity: if > 20%, skip rewrite for that term
     7. Query the inverted index at optimization time → get matching row_t[]
     8. Create LogicalColumnDataGet with row IDs (same pattern as
     InClauseRewriter)
     9. Create LogicalComparisonJoin(MARK) joining original scan with row IDs on
      rowid
     10. Keep original filter expression for correctness (handles edge cases, no
      cost since only matching rows remain)

     creating MARK joins with in-memory data.

     - No persistence: Index is in-memory only. Rebuilt on restart.

⏺ Good question. Let me map each characteristic to concrete optimizations — some
   already in our extension, some next steps.

  1. Time-ordered, append-only, immutable

  What it enables:
  - Segment-level timestamp pruning — already implemented. Skip entire row-group
   partitions by [ts_min, ts_max].
  - No cache invalidation — immutable segments mean cached posting lists,
  dictionaries, search results never go stale. Cache everything aggressively.
  - No delete tracking needed — logs aren't updated. Our TryDelete no-op is
  actually correct for the log use case, not a hack.
  - Sorted posting lists for free — rows arrive in order, so row IDs in posting
  lists are naturally sorted during build. No sort step needed.

  Next step for our extension: Add a result cache. Same contains(msg, 'error')
  on same partition → return cached result. Husky reports 80% hit rate because
  dashboards auto-refresh.

  2. Skewed-recent access (80%+ queries hit last few minutes)

  What it enables:
  - Pin recent partitions in memory, evict old ones. Most queries only touch the
   last N partitions. Keep their dictionaries and posting lists hot.
  - Limit ORDER BY ts DESC LIMIT N — for needle-in-haystack queries, scan
  partitions in reverse chronological order. Stop as soon as LIMIT is satisfied.
   Never touch old partitions at all.
  - Tiered storage — recent partitions: full inverted index in memory. Older
  partitions: compressed on disk, only loaded on demand. Oldest: just zone maps,
   no index.

  Next step for our extension: Reverse-order partition scan for ORDER BY ts DESC
   LIMIT N. Currently we scan all partitions and return all matching row IDs.
  Instead: iterate partitions from newest → oldest, stop when we have enough
  rows. This is a huge win for the common LIMIT 100 case — avoid touching 99% of
   data.

  3. Write-heavy, read-light

  What it enables:
  - Batch index builds, not per-row — already doing this. Build callbacks
  process chunks, not individual rows.
  - Async index build — new data visible immediately via scan, index built in
  background. Queries fall back to column scan on unindexed segments. ClickHouse
   does this.
  - Minimize per-row index work — don't index everything. Index the message
  column, use zone maps for structured fields like service/level. Our WITH 
  (timestamp_column = 'ts') pattern generalizes to: declare which columns get
  which index type.

  Next step: Background index build for new row groups appended after index
  creation. Currently Append creates a new partition on-the-fly, but it's not
  optimized for high-throughput ingestion.

  4. Schemaless / wide / sparse

  What it enables:
  - Per-column indexing control — not every column needs an inverted index.
  Structured fields (service, level) work fine with zone maps. High-cardinality
  IDs (trace_id) want bloom filters. Only message/body needs full-text.
  - Don't require schema upfront — index whatever columns exist. New fields
  appear automatically if using JSON/MAP columns.

  Next step: Support indexing JSON/MAP columns. Extract keys and values, index
  them separately. WHERE json_col->>'error_type' = 'timeout' should hit the
  index.

  5. High cardinality

  What it enables:
  - Bloom filters complement inverted index — for trace_id = 'abc-123' (billions
   of unique values), an inverted index has one-entry posting lists = wasteful.
  Bloom filter per partition is cheaper: "does this partition maybe contain this
   trace_id?" Skip if no. Scan if yes.
  - Dictionary compression — high cardinality means large dictionaries. But
  within a partition (~122K rows), cardinality is bounded. Dictionary per
  partition stays manageable.

  6. Two query shapes: needle vs. analytics

  Needle-in-haystack (WHERE trace_id = 'abc' AND ts > ...):

  - Critical: early termination. Don't scan all partitions if first match

  Analytics (SELECT service, count(*), p95(duration) FROM logs WHERE ts > ...

  - Touches many rows, few columns. Not selective.

  already does this — the join filters rows, downstream operators aggregate.

  7. Interactive latency

  What it enables:
  - Streaming partial results — return first N matches as soon as found, don't

  - Partition-level parallelism — search multiple partitions concurrently, merge
   results.
  - Approximate counts — for count(*) with text filter, could use posting-list

  Next step: For SELECT count(*) FROM logs WHERE contains(msg, 'error'), the

  Correctness Issues

  1. contains() rewrite is semantically wrong

  contains(msg, 'connection timeout') does substring match. Our tokenizer splits
   it into ["connection", "timeout"] and intersects posting lists. This finds
  rows containing both tokens anywhere — but the original contains checks for
  the exact substring "connection timeout" as a contiguous sequence. Our rewrite
   is a superset.

  Keeping the original filter as post-filter saves us from returning wrong
  results. But if someone writes contains(msg, 'on tim'), the tokenizer produces
   ["tim"] (single char "on" gets dropped). We'd return all rows with "tim"
  anywhere — much wider than intended. The post-filter catches it, but the
  "optimization" could return more rows than a full scan would process.

  Verdict: Not a bug (post-filter is correct), but the index may hurt
  performance for substring-that-isn't-a-token-boundary queries. Should only
  rewrite when we're confident the index narrows well.

  2. col = 'exact_value' rewrite is wrong for exact match semantics

  WHERE msg = 'error connection timeout' should match only rows with that exact
  string. We tokenize to ["error", "connection", "timeout"] and intersect
  posting lists. This returns all rows containing all three tokens — which
  includes rows like "timeout error in connection pool". The post-filter saves
  correctness, but the index may not narrow much.

  Verdict: Same as above — correct but potentially unhelpful. For exact match,
  should we instead index the full value as a single dictionary entry?

  3. Append creates broken partitions

  AddRow creates a partition with row_count = 1 for row IDs not in any existing
  partition. After multiple appends, you get many single-row partitions. Also,
  the D_ASSERT(local_offset > data_.back()) in PostingList::Add will fire if
  appends arrive out of order within a new partition.

  4. No MVCC awareness

  The index is queried at optimization time (before execution). If a concurrent
  transaction inserts/deletes rows between optimization and execution, the row
  IDs may be stale. The post-filter mitigates false positives, but we could miss
   rows inserted after optimization. For append-only logs this is acceptable,
  but worth noting.

  Performance Issues

  5. Materializing all row IDs into a ColumnDataCollection

  For a term matching 100K rows, we create a 100K-row in-memory table and
  MARK-join it. This is expensive — the join itself may be slower than a scan.
  The 20% selectivity threshold helps, but even at 19% of 10M rows = 1.9M row
  IDs materialized.

  Better: Use a SEMI join instead of MARK join (avoid the boolean mark column).
  Or even better: skip the join entirely and use a direct index scan path (the
  proper DuckIndexScanState approach). The current approach is O(N log N) for
  the join; a direct scan is O(matches).

  6. Optimizer queries index at plan time — O(result set) memory

  The optimizer materializes all matching row IDs in memory during planning. For
   large result sets this uses lots of memory and slows planning. Should be lazy
   — produce row IDs during execution, not planning.

  7. Only rewrites one expression per filter

  The break at the end means WHERE contains(msg, 'error') AND contains(msg, 
  'timeout') only rewrites the first predicate. Should rewrite both (intersect
  the result sets).

  8. Timestamp extraction doesn't handle BETWEEN

  WHERE ts BETWEEN '2024-01-01' AND '2024-01-02' gets rewritten by DuckDB to ts 
  >= ... AND ts <= ... inside a CONJUNCTION_AND. Our ExtractTimestampBounds only
   looks at top-level filter expressions, not inside conjunctions.

  9. std::map dictionary is slow

  std::map has poor cache locality. For a partition with 10K unique terms, every
   lookup is pointer-chasing through tree nodes. A sorted vector<pair<string, 
  idx_t>> with binary search would be faster and more serialization-friendly. Or
   a hash map for lookup + sorted vector for prefix search.

  Structural Issues

  10. No persistence

  Known. Index is lost on restart, checkpoint, or database reopen.

  11. No LIKE pattern handling

  WHERE msg LIKE '%error%' is never matched by the optimizer. It's a
  BoundFunctionExpression with function name ~~ (the LIKE operator), not
  contains. DuckDB may also rewrite LIKE 'prefix%' to range comparisons that we
  don't catch.

  12. No multi-column index support

  Can only index one column. For log search, often want message + service +
  level in one index.

  13. No index rebuild/refresh mechanism

  After many appends, the index degrades (new rows in broken single-row
  partitions, stale selectivity estimates). No way to rebuild short of DROP +
  CREATE.

  Open Questions

  1. Should the index store full values as dictionary entries (for exact match) 
  in addition to tokens? Would enable true col = 'value' support.
  2. Is MARK join the right approach, or should we push toward SEMI join or 
  direct index scan? MARK join adds overhead. The proper long-term answer is the
   DuckIndexScanState path but requires changes to table_scan.cpp.
  3. How to handle the index during checkpoint? DuckDB may reassign row IDs
  during compaction. The index needs to survive this or be rebuilt.
  4. Should the optimizer rewrite happen in pre_optimize_function instead of 
  optimize_function? Running after built-in optimizers means some expressions
  may already be rewritten (LIKE → range, IN → join) in ways we don't recognize.
  5. Thread safety of index reads during optimization — the optimizer runs in
  the main thread, but the index was built with data visible at build time.
  Concurrent appends to the table could modify the index's partitions while the
  optimizer reads them.

  1. Deleting index metadata for old rows

  The log use case has bulk retention: drop everything older than 7 days. Not
  row-by-row deletes.

  Per-partition design makes this clean. Each partition is aligned with a row
  group and has ts_min/ts_max. To drop old index data:

  for partition in partitions:
      if partition.ts_max < retention_cutoff:
          drop partition (free dictionary + posting lists)

  This is O(partitions dropped), no per-row work. Dictionaries and posting lists
   are freed in bulk.

  Three triggering mechanisms:

  ┌──────────────┬──────────────────────────────────────────────────────────┐
  │   Trigger    │                           How                            │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ Explicit     │ CALL logsearch_prune('idx', '7 days') — user-invoked     │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ On query     │ Before searching, skip AND lazily drop partitions with   │
  │              │ ts_max < now() - retention. Amortized cleanup.           │
  ├──────────────┼──────────────────────────────────────────────────────────┤
  │ On DuckDB's  │ When DuckDB drops row groups (via DELETE WHERE ts <      │
  │ own          │ cutoff + VACUUM), our TryDelete callback fires.          │
  │ retention    │ Currently a no-op — should detect "entire partition      │
  │              │ deleted" and drop it.                                    │
  └──────────────┴──────────────────────────────────────────────────────────┘

  The key insight: because partitions are immutable and time-bounded, retention
  is partition-drop, not row-delete. Same pattern as Husky dropping old
  fragments or ClickHouse dropping old parts. No tombstones, no compaction of
  deleted entries — just free the whole partition.

  Edge case: Partially-expired partitions (ts_min < cutoff < ts_max). Options:
  - Keep the whole partition (simple, waste some memory)
  - Rebuild partition with only surviving rows (expensive, rarely worth it)
  - Mark as "partially expired" and let the post-filter handle correctness

  I'd go with "keep it" — the partition gets dropped entirely when its ts_max
  passes the cutoff too. For a 7-day retention with ~122K-row partitions, a
  partition spans maybe minutes. The overlap window is tiny.

  2. Batch processing: where do batches come from?

  During initial CREATE INDEX: The IndexType build callbacks handle this. DuckDB
   scans the table in chunks (STANDARD_VECTOR_SIZE = 2048 rows), sends each
  chunk to build_sink. Multiple threads produce local indexes. build_combine
  merges them. build_finalize returns the complete index. This is batch
  processing — we never see individual rows.

  During ongoing inserts: After the index exists, BoundIndex::Append is called
  per-chunk as data is committed. Currently we tokenize and add immediately.
  This is the hot path where you want to be fast.

  The commit question: DuckDB's append flow:

  INSERT INTO logs VALUES (...)
    → DataTable::LocalAppend()     [writes to local storage, not yet visible]
    → COMMIT
      → DataTable::CommitAppend()   [makes rows visible]
      → BoundIndex::Append()        [called with committed row IDs]

  So yes, Append is called after commit, with the final row IDs. The data is
  already durable.

  In-memory-first, disk-later architecture:

  New data arrives
    → Build "hot" in-memory partition (tokenize, build dictionary + posting
  lists)
    → Hot partition is immediately searchable
    → Background thread: serialize hot partition to disk
    → Once on disk, convert to "cold" partition (memory-mapped or loaded on
  demand)

  Query path:
    → Search hot partitions (in memory)
    → Search cold partitions (from disk/mmap)
    → Merge results (concatenation — already sorted by row_start)

  class LogsearchIndex {
      // Hot: recently built, fully in memory, not yet persisted
      vector<unique_ptr<IndexPartition>> hot_partitions;

      // Cold: persisted to disk, loaded on demand
      vector<unique_ptr<DiskPartition>> cold_partitions;

      // Background worker
      std::thread background_worker;
      ConcurrentQueue<IndexPartition*> flush_queue;
  };

  When Append is called:
  1. If row belongs to an existing hot partition → add to it
  2. If hot partition is "full" (partition's row group is complete) → enqueue
  for flush
  3. Background worker dequeues, serializes to disk, replaces hot → cold

  ClickHouse does with its three-file format (.dct, .idx, .pst).

  3. Low-cardinality attributes in the index

  You're identifying a real problem. Consider:

  Row group 0: services = {api, web, worker, cron}     → zone map: min=api,
  max=worker
  Row group 1: services = {api, web, worker, cron}     → zone map: min=api,
  max=worker
  Row group 2: services = {api, web, worker, cron}     → zone map: min=api,
  max=worker

  Zone maps are useless here — every row group contains every service. WHERE 
  service = 'api' scans every row group.

  Putting low-cardinality attributes in the inverted index solves this:

  Partition 0, dictionary:
    "service:api"     → posting list [0, 4, 8, 12, ...]      (25% of rows)
    "service:web"     → posting list [1, 5, 9, 13, ...]      (25% of rows)
    "service:worker"  → posting list [2, 6, 10, 14, ...]     (25% of rows)
    "service:cron"    → posting list [3, 7, 11, 15, ...]     (25% of rows)

  Now WHERE service = 'api' AND contains(message, 'timeout'):
  1. Intersect service:api posting list with message:timeout posting list
  2. Result: only rows where both match
  3. Maybe 0.25% of rows instead of scanning everything

  This is better than bloom filters for low-cardinality. Bloom filters answer
  "maybe yes / definitely no" per partition. For low-cardinality fields that
  appear in every partition, bloom filters always say "maybe yes" — useless. The
   inverted index gives exact row-level filtering.

  Design for multi-column indexing:

  CREATE INDEX idx ON logs USING logsearch(message, service, level)
  WITH (timestamp_column = 'ts');

  Internally, prefix terms with column name to avoid collisions:

  Dictionary entries:
    "message:error"          → posting list
    "message:timeout"        → posting list
    "service:api"            → posting list
    "service:web"            → posting list
    "level:error"            → posting list (note: different from
  "message:error")
    "level:warn"             → posting list

  The optimizer matches:
  - service = 'api' → look up "service:api" (exact, single entry)
  - level = 'ERROR' → look up "level:error" (after lowercasing)
  - contains(message, 'timeout') → look up "message:timeout"
  - Compound: intersect all matching posting lists

  This is exactly Husky's approach — "standard text fields" and "all other
  attributes" share the same index, just with different key prefixes.

  When is this NOT a good idea?

  High-cardinality structured fields like request_id or user_id. With millions
  of unique values, the inverted index dictionary gets huge and each posting
  list has ~1 entry. Bloom filters are better here (fixed size, no per-value
  storage). The right answer is: inverted index for text + low-cardinality, 
  bloom filters for high-cardinality exact match, zone maps for 
  timestamps/numerics. Different tools for different cardinalities.
